# CLAUDE.md

GNOME Shell extension `desktop-mouse-nav@redcodeworks.github.io` (GPL-2.0-or-later, public repo `redcodeworks/gnome-shell-extension-desktop-nav`; the local directory keeps the old name `desktop-mouse-nav`). Target: GNOME Shell 51 (Fedora 45, Wayland). Mouse button RULES run an action (mouse buttons only, no keyboard keys): a rule is (button number, modifiers, action id), kept in one list per context: `desktop` (pointer on the empty desktop; default Back/8 = previous workspace, Forward/9 = next), `shell` (other Shell surfaces such as the top bar), `overview` and `app-grid` (while open and enabled); edited in the preferences window (0.3.0). Mouse wheel rules are a separate later brief (not built); a rule's input is `{kind: 'button', button}` so another input type fits later. There is NO context for application windows: mutter filters button events before Clutter, so presses on client windows never reach the Shell and a stage `captured-event` handler only sees presses over Shell UI actors (GNOME Shell maintainer on Discourse, 2020, plausibly still valid for 51; not re-verified, hub research). The UI says so; do not reintroduce an "anywhere" context.

## Layout
Subdirectory layout: the extension lives in `desktop-mouse-nav@redcodeworks.github.io/` (`extension.js`, `prefs.js`, `actions.js`, `metadata.json`, `schemas/*.gschema.xml`) so the repo root can hold LICENSE, README, justfile, CI. `gnome-extensions pack <dir>` accepts a source directory, so no flat layout is needed.

## Design
- ESM; `extension.js` default-exports a class extending `Extension`; `prefs.js` a class extending `ExtensionPreferences` (libadwaita: one `Adw.PreferencesPage`; one `Adw.PreferencesGroup` per context in the order desktop, shell, overview, app grid; the overview and app grid groups start with their `Adw.SwitchRow` (`work-in-overview`, `work-in-app-grid`); then groups "Workspaces" (`wrap-workspaces`) and "Advanced" (`debug-log`), switches bound by plain `settings.bind`). Each rule is an `Adw.ActionRow` (title = button name; suffixes: modifier `Gtk.DropDown`, action `Gtk.DropDown`, flat `user-trash-symbolic` delete button); an `Adw.ButtonRow` ("Add rule", `list-add-symbolic`) closes each list; an empty list shows a dimmed "No rules yet" row. Rows are rebuilt from the setting on `changed::<key>` and after add/delete; in-place edits write back with `settings.set_value(key, new GLib.Variant('a(uss)', ...))` under an echo guard (reading: `get_value(key).recursiveUnpack()`); an edit that would duplicate a rule or make an unbindable one is reverted with a toast. NEVER use `bind_with_mapping` in prefs.js: its GJS callback conventions made the prefs process core-dump on a real Shell 51 ("schema default value ... rejected by the binding mapping function", Extension Manager showed "GNOME Shell Unavailable"). `window._settings` keeps the settings alive. The preflight skips the connect/disconnect pairing rule for prefs.js (own process, ends with the window). `tests/test-settings.sh` fails if prefs.js uses a binding mapping or imports anything but Adw/Gio/Gtk/GLib/GObject.
- Add-rule dialog (`showRuleDialog` in prefs.js): `Adw.Dialog` ("Press a mouse button", libadwaita 1.5) presented with `dialog.present(window)`; on an exception a modal `Adw.Window` with `transient_for` is the fallback. A `Gtk.GestureClick` (`button = 0`, CAPTURE phase) reads `get_current_button()` and `get_current_event_state() & Gtk.accelerator_get_default_mod_mask()` in `pressed`; modifier bits via `modifiersFromState(state, GTK_MASKS, false)` (GDK 4 values hard-coded in actions.js because Gdk is not imported). Buttons 1 and 3 show a message and detection continues (the gesture does not claim the sequence, so Cancel still works). After detection the button, a modifier `Adw.ComboRow` (16 combinations, "None" first) and an action `Adw.ComboRow` appear with Add (disabled while the combination is unbindable or already bound) and Cancel.
- `actions.js` is the single source of truth (no imports, so node can run it in tests): schema id, `CONTEXTS` (desktop, shell, overview, app-grid), `rulesKey(context)` = `rules-<context>`, `ACTIONS` (id + label), the rule model (`makeRule`, `parseRules`, `serializeRules`, `normalizeModifiers`, `MODIFIER_COMBOS`, `modifierLabel`, `buttonName`, `unbindableReason`, `findDuplicate`, `matchRule`, `anyRuleUsesButton`, `contextOrder`, `findRule`, `modifiersFromState`, `GTK_MASKS`) and the rest of the pure logic tests cover without a Shell: `pointerContext`, `resolveAction` (app grid: prev/next workspace -> page step), `pageTarget(current, nPages, step)` (no wrap, null at the ends, one page, zero pages), `workspaceTarget(active, count, step, wrap)`, `overviewAllowed`, `debugLine(enabled, button, mods, context, found, result)` (null when off). Both extension.js and prefs.js import it; the pre-flight WARNs about the extra JS module (fine, it is imported).
- Schema `org.gnome.shell.extensions.desktop-mouse-nav` (`metadata.json` `settings-schema`): four rule keys of type `a(uss)` (button, modifier string, action id): `rules-desktop` (default `[(8, '', 'prev-workspace'), (9, '', 'next-workspace')]`), `rules-shell`, `rules-overview`, `rules-app-grid` (default `[]`). Modifier strings are normalized and sorted alphabetically: parts `alt`, `ctrl`, `shift`, `super` joined by `+` (`ctrl+shift`), `''` for none. `parseRules` drops invalid entries (buttons 1 and 3, a bare middle button, unknown modifiers or action ids). The old keys `desktop-back`, `desktop-forward`, `shell-back`, `shell-forward` are removed in 0.3.0 without migration (0.2.0 had one user). The zip ships the XML only, never `gschemas.compiled` (`just pack` passes `--schema=schemas/...xml` and `--extra-source=actions.js`; verified that the zip then holds no compiled schema). `glib-compile-schemas --strict` accepts the non-empty tuple-array default (checked, and read back with `gsettings --schemadir` in `tests/test-settings.sh`).
- Four boolean keys, all default `false`: `work-in-overview` ("Enable for the Overview"), `work-in-app-grid` ("Enable for the app grid"), `wrap-workspaces` and `debug-log`. `overviewAllowed(state, flags)` in `actions.js` decides (grid showing -> only with the grid flag; else overview visible -> only with the overview flag; else always); the handler propagates the press when it says no. `Main.overview.toggle` while the overview is open closes it; the app grid action while the grid is showing is handled in `_toggleAppGrid`.
- Buttons and modifiers: any button except 1 (primary) and 3 (secondary), which are refused in the editor and never touched by the Shell side; middle (2) only with at least one modifier. Names: 2 Middle, 8 Back, 9 Forward, others "Button N". Two rules in one context with the same (button, modifiers) are refused in the editor ("already bound"); the Shell side takes the first match. Matching is on the EXACT modifier set: `event.get_state()` is reduced by `modifiersFromState(state, MODIFIER_MASKS, true)` to Shift, Control, Mod1 (Alt) and Super; `LOCK_MASK`, `MOD2_MASK` and the `BUTTONn_MASK` bits are ignored; any other bit (Hyper, Meta, Mod3..5) makes the press match no rule.
- Actions, Shell API only (no key synthesis, no processes): `prev-workspace`, `next-workspace` (`workspace.activate`), `toggle-overview` (`Main.overview.toggle()`), `toggle-app-grid` (`Main.overview.showApps()`, hide when the app grid is already showing), `move-window-prev-workspace`/`-next-workspace` (focused NORMAL window not on all workspaces: `window.change_workspace`, then `workspace.activate_with_focus`), `none`. Workspace moves stop at the ends (no wrap, `WRAP` constant).
- Context resolution (`pointerContext`, `findRule`, `contextOrder`): with the overview open the context is `app-grid` or `overview` (gated by the switches) and only that context's rules are tried; otherwise `desktop` (pointer on the empty desktop) tries the desktop rules first and then the shell rules, and `shell` (another Shell surface) tries only the shell rules. First matching rule wins. These replace the 0.2.0 behavior where the overview and app grid used the desktop action.
- App grid paging: while the app grid shows, `prev-workspace`/`next-workspace` call `appDisplay.goToPage(_grid.currentPage -/+ 1)` (via `resolveAction`/`pageTarget`; no wrap, at the first/last page or with the grid unavailable the press propagates; `AppDisplay.goToPage` clamps, `IconGrid.goToPage` throws, so only `AppDisplay.goToPage` is called). Other actions behave as bound. Grid access: `Main.overview.controls` or `Main.overview._overview.controls`, then `.appDisplay`; app grid detection `controls._stateAdjustment.value >= ControlsState.APP_GRID (2) - 0.001` (namespace import of `overviewControls.js`, fallback 2), else the dash `showAppsButton.checked`. Everything is wrapped so a missing API propagates the press and never throws.
- Wrap: `wrap-workspaces` (cached in `_loadActions`) feeds `workspaceTarget` for workspace switching and window moves (not for app grid pages). One workspace or target equals active: propagate. The trailing dynamic empty workspace counts as the last one. (Actions run as in 0.2.0, including no key synthesis.)
- `enable()` gets the settings, caches the parsed rules of all four contexts (`_loadActions`, reloaded on the settings `changed` signal; a press never reads GSettings) and connects `global.stage` `captured-event`; `disable()` disconnects both and drops the references. No timers.
- Press handler cost: buttons 1 and 3 propagate at once; a release is swallowed only when its press was; a press of a button that no rule in any context uses propagates before anything else (`anyRuleUsesButton`); then locked/modal checks, the exact modifier set, `overviewAllowed`, and only when a desktop rule uses the button the `get_actor_at_pos(REACTIVE)` lookup (the background check is a `Meta.BackgroundActor` or inside `Main.layoutManager._backgroundGroup`, never while the overview is visible). The press is consumed (`EVENT_STOP`) only when an action ran, and the matching release is swallowed; everything else returns `EVENT_PROPAGATE`.
- Logging: only with the `debug-log` setting (off by default). One `console.debug` line per handled press (`debugLine`: button, modifiers (`none`/`ctrl+shift`/`other` for unknown bits), pointer context, rule `<list>[<index>]` or `none`, action, result ran/propagated/at-end); the single `console.debug` call sits behind `if (this._debug)` and `if (line)`, tests check that. Read with `journalctl --user -b -o cat | grep desktop-mouse-nav`. The pre-flight WARNs about console.debug (never FAIL; only console.log fails).

## Versioning (Kevin, 2026-11-09)
Semantic versioning in `version-name`, 0.x until the extension is actually published on extensions.gnome.org. Never propose 1.0.0 before publishing. A new feature is a minor bump (the settings feature is 0.2.0, the mapping editor 0.3.0), a fix a patch bump. `promote` releases only a `version-name` whose tag does not exist yet.

## Testing
```
just lint        # JSON + JS syntax (extension.js is checked as a temp .mjs copy)
just pack        # dist/*.zip (dist/ is gitignored)
just install-local   # pack, then unzip into ~/.local/share/gnome-shell/extensions/<uuid> (replaces that uuid only)
just enable      # gnome-extensions enable; fails until the Shell knows the extension (log out and in first)
just uninstall   # disable if known, remove the directory
just status      # gnome-extensions info + whether the directory exists
just test        # lint + temp-dir install/uninstall (GNOME_EXTENSIONS_DIR) + tests/test-*.sh; home untouched
just install [VERSION] [--testing] [--dry-run]   # download: latest release, a VERSION, or the rolling testing prerelease; checksum verified
```
`just test` checks packaging, install mechanics and the pipeline scripts, never the extension's runtime behavior (that needs a live Shell). The justfile `uuid` must match `metadata.json` (`install-local` refuses otherwise).

Manual run: `just install` (or `--testing`, or `install-local`), log out and in (Wayland), `just enable`, watch logs with `journalctl -f -o cat /usr/bin/gnome-shell` (debug lines need debug logging enabled, e.g. `G_MESSAGES_DEBUG=all`). Test: click Back/Forward on empty desktop, on a window, in the overview.

## Branching (GitLab Flow, production-branch variant; Kevin, 2026-11-09)
Same model as octarine-os (its PR #23). Written for the repo settings Kevin applies afterwards; NOT yet exercised on GitHub (the `pull_request` path of `ci.yml` and `require-testing-branch` have never run).
- Environments: dev = the validation run on a PR (`test` and `secrets`, nothing published), UAT = the rolling `testing` prerelease (`just install --testing`), prod = the release (`just install`). `testing` is the integration branch (GitLab's "main"), `main` the production branch. Changes move one way, downstream: `feat/<topic>` or `fix/<topic>` -> PR into `testing` -> PR from `testing` into `main` (the promotion). Fixes go upstream first.
- Rebase and merge everywhere (repo setting, applied by Kevin), so `main` never has commits `testing` lacks and there is no back-merge. Until then merge commits are allowed and the tree-based promote lookup copes with any merge style.
- Hotfix: fix on a `fix/<topic>` (or `hotfix/<topic>`) branch into `testing`, then promote. Only when `testing` is broken and prod needs an emergency fix: PR it into `main` (the `require-testing-branch` check must be bypassed by Kevin) and immediately cherry-pick it into `testing`.
- PR runs are validation only: the zip is built once per change by the push to `testing` (the PR merge into `testing`), and that build is what `promote` releases by tree. So a PR run must never upload an `extension-<tree>` artifact (promote would then see a build that no `testing` run produced) and never run `publish-testing`.
- `require-testing-branch.yml`: job `require-testing-branch`, `pull_request` into `main`, `permissions: {}`, no checkout; fails unless the head branch is `testing` of this repo. Never runs for PRs into `testing`. Make it a required check on `main` next to `test` and `secrets`.
- The other project repos (hub-managed) still commit straight on `testing`; only this repo and octarine-os use feature branches.

## CI and release pipeline (build once, promote)
Design (written 2026-11-09, NONE of it has run on GitHub yet when this was written):
- `.github/workflows/ci.yml`, push to `testing` (the real build) and `pull_request` into `testing` (validation only, see Branching); a push to any other branch triggers nothing. PR runs skip the artifact upload and `publish-testing`. Jobs `test` (Fedora 45 container: `just test` = lint + temp-dir install + `tests/test-*.sh`, schema compile only if `schemas/*.gschema.xml` exists, `just pack`, `scripts/make-manifest.sh`, upload artifact) and `secrets` (gitleaks 8.30.1 over the full history, pinned download with sha256 and `curl --retry`). **Required check names on `main`: `test` and `secrets`; keep them stable.** Artifact name `extension-<tree sha>`, files: `<uuid>.shell-extension.zip` and `manifest.json` (uuid, version-name, commit, tree, zip, zip_sha256, shell-version), kept 90 days. Concurrency: one group per PR (cancel in progress) and one per ref for pushes, so a newer push to `testing` cancels the older one.
- `.github/workflows/promote.yml`, push to `main`. `scripts/promote.sh` finds the artifact `extension-<tree of the new main commit>` from a run on `testing` with conclusion success (tree equality works for merge, squash and rebase merges; no second-parent logic), downloads it with `gh run download`, checks the zip sha256 against the manifest, manifest tree and uuid, and that `metadata.json` inside the zip has the same uuid and version-name as the tree. Then attest (`actions/attest-build-provenance`) and `gh release create v<version-name>` with the zip and a `.sha256`. Never rebuilds. No matching tested build: the job FAILS and publishes nothing. Only this job has `contents`, `id-token`, `attestations` write (and `actions: read`).
- Versioning: `version-name` in `metadata.json` is bumped BY HAND (EGO: 1-16 characters of letters, numbers, spaces, periods; no hyphens; the promote job also refuses spaces because of the tag). The tag is `v<version-name>`. If the tag exists, promote does not release and ends GREEN with a notice "bump version-name to release" (so merging without a bump releases nothing). No `version` field (EGO assigns it). Testing builds are also published as the rolling `testing` prerelease (see below). Merging the first PR with `0.1.0` releases `v0.1.0`. v0.1.0 is released; the next bump (0.1.1) carries the review-guideline fixes.
- `.github/workflows/prepare-ego.yml`, `workflow_dispatch` only (input `ref`, default `main`): builds the zip, runs `scripts/ego-preflight.sh` (FAIL = hard rule, WARN = heuristic), uploads `ego-<version-name>.zip` + `.sha256` + report (zip only when the pre-flight passes) and writes the report plus `scripts/ego-manual-steps.md` into the job summary. It uploads nothing to EGO and stores no credentials (no documented upload API). The pre-flight rules are OUR reading of https://gjs.guide/extensions/review-guidelines/review-guidelines.html (research by the hub, 2026-11-09; the agent has no web access): heuristics, a pass is no guarantee. Severities: FAIL = hard rule (`version` field, empty `donations`, shell-version not majors, more than ONE `.alpha`/`.beta` development entry or a stable major above it, media/script/binary/.po files, minified lines, missed disconnects, ...); WARN = redundant or unverified: `session-modes: ["user"]` (redundant, not banned), `schemas/gschemas.compiled` and a missing LICENSE in the zip ("not stated in the guidelines (unverified)"). `just pack` puts LICENSE into the zip root via `gnome-extensions pack --extra-source=<abs path>/LICENSE` (checked locally: lands at the root; also with a relative path from inside the source dir); `tests/test-pack.sh` lists the zip. The manifest and promote checks only look at the zip sha256, uuid and version-name, so they are unaffected. The guidelines also say AI use is allowed but the developer must be able to justify and explain the code (quoted in `scripts/ego-manual-steps.md`).
- Shexli (optional step in `prepare-ego.yml`, report only): EGO review team's static analyzer, PyPI `shexli==0.2.1`, installed with a uv 0.13.7 musl release download (sha256 checked, `curl --retry`) into a `uv venv --python 3.12`, run on the staged `ego-<version-name>.zip` with `python -m shexli --format text|json PATH` (verified locally; the exit code is 0 even with findings). Output goes to the job summary and the `shexli-report` artifact; the step has `continue-on-error` and ends `exit 0`, never fails the job, and is not authoritative. Local run on the packed zip reported EGO-M-004 for `shell-version: ["51"]` (it considers 51 an implausible future release or invalid, probably an outdated built-in release table; UNVERIFIED reason, a reviewer-facing question for Kevin). Never run on GitHub yet.
- `.github/workflows/gnome-version-watch.yml`, weekly (Wed 06:23 UTC) and manual, in a `fedora:latest` container (the one deliberately unpinned image: it must track the current release): `scripts/gnome-version-watch.sh` runs `dnf repoquery gnome-shell` (queryformat `name|epoch|version|release|arch|repoid`) over channels in order `branched rawhide released` (override with `CHANNELS`), FIRST that answers wins and is logged. `branched` = releasever released+1 with `fedora,updates,updates-testing`; when it does not resolve (no beta yet) it is skipped with a log line. `rawhide` = `--releasever=rawhide` with the repo id READ from `/usr/share/dnf5/repos.d/fedora-rawhide.repo` (package `fedora-repos-rawhide`, installed by the workflow; the stock fedora-repos-45 has no rawhide repo id); without that file the channel is skipped. The major (leading digits, `52.alpha`/`52~beta`/`52~alpha.1` -> 52) is compared numerically with the max of `shell-version`; if larger, one issue `Support GNOME Shell <N>` with label `gnome-version` (created when missing) and a checklist; deduped on any open `gnome-version` issue or same title. Only this workflow has `issues: write`. The version string is only regex-matched, never evaluated. Verified by the hub in a fedora-toolbox:45 container: `--repo`, `--latest-limit`, `--queryformat` work, `--releasever=46 --repo=fedora` returned 51.1. UNVERIFIED: the repo id inside `fedora-rawhide.repo`, the branched channel before a beta exists, and that the workflow has ever run on GitHub.
- Rolling testing prerelease (written 2026-11-09, NEVER RUN on GitHub yet; the first push to `testing` after it landed is its test): job `publish-testing` in `ci.yml`, `needs: [test, secrets]`, `if: github.ref == 'refs/heads/testing'`. The only job in `ci.yml` with `contents: write` (plus `actions: read`). The `test` job exposes its `tree` output; `publish-testing` runs `gh run download $GITHUB_RUN_ID -n extension-<tree>` (no download-artifact action, so no extra pin), checks the zip sha256 and tree against `manifest.json`, writes the `.sha256`, deletes the old release (`gh release delete testing --cleanup-tag --yes` when it exists) and creates the PRERELEASE `testing` (tag `testing`, never `v*`) on `$GITHUB_SHA` with the zip, `.sha256` and `manifest.json`. Title `testing (<version-name>, <short sha>)`; the body says UAT build, commit, tree, run URL. Never rebuilds. `promote.yml` is untouched: it only creates `v<version-name>` (version-name is `[0-9A-Za-z.]{1,16}`, the tag always starts with `v`, so `testing` can never be one) and looks the artifact up by tree. `gh release view` without a tag returns the latest NON-prerelease, which is how `just install` ignores `testing`. A cancelled run (newer push) between delete and create leaves no testing release until the next push passes.
- Install: `just install [VERSION] [--testing] [--dry-run]` (`scripts/install-remote.sh`; no argument = `gh release view` tag of the latest real release, VERSION = `v<VERSION>`, `--testing` = tag `testing`; `--testing` with a VERSION is a usage error; unknown option usage on stderr, exit 1; no release yet says so and points to `just install --testing` and `just install-local`). It downloads `*.zip` and `*.sha256` with 3 attempts (`RETRY_WAIT` seconds apart, "not found" is not retried), checks the checksum, and installs through `scripts/install-zip.sh` (which compiles the schema). Idempotent: "already installed" when the installed `version-name` and the zip sha256 match; `install-zip.sh` records the zip sha256 in `<extdir>/.<uuid>.zip-sha256` (removed by `just uninstall`). `just install-local` builds the working tree (`just pack`) and unpacks it; it was `install` before, `install-release` was folded into `install` (no aliases, Kevin's rule).
- Settings required in the GitHub repository (Kevin): branch protection on `main` requiring `test` and `secrets`; Actions allowed to create releases and issues (workflow permissions).

## Why install unpacks the zip
The unpack route (`scripts/install-zip.sh`) compiles the schema (`glib-compile-schemas --strict` in the staging directory; fails and keeps the old copy when the tool is missing, Fedora package glib2-devel), because only EGO and `gnome-extensions install` compile it automatically. Found on a real Shell (0.2.0 failed with `GLib.FileError ... schemas/gschemas.compiled: No such file`); CI cannot load the extension in a Shell, so this class of bug is only caught by a real session. A hand-unpacked release zip needs `glib-compile-schemas schemas/` run inside the extension directory.
