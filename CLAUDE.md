# CLAUDE.md

GNOME Shell extension `desktop-mouse-nav@redcodeworks.github.io` (GPL-2.0-or-later, public repo `redcodeworks/gnome-shell-extension-desktop-nav`; the local directory keeps the old name `desktop-mouse-nav`). Target: GNOME Shell 51 (Fedora 45, Wayland). Mouse Back/Forward (buttons 8/9) run a configurable action (preferences window), per context: `desktop` (pointer on the empty desktop, default prev/next workspace) and `anywhere` (default none).

## Layout
Subdirectory layout: the extension lives in `desktop-mouse-nav@redcodeworks.github.io/` (`extension.js`, `prefs.js`, `actions.js`, `metadata.json`, `schemas/*.gschema.xml`) so the repo root can hold LICENSE, README, justfile, CI. `gnome-extensions pack <dir>` accepts a source directory, so no flat layout is needed.

## Design
- ESM; `extension.js` default-exports a class extending `Extension`; `prefs.js` a class extending `ExtensionPreferences` (libadwaita: one `Adw.PreferencesPage`, a group per context, a `Adw.ComboRow` per button, then an "Overview" group with two `Adw.SwitchRow`s). NEVER use `bind_with_mapping` in prefs.js: its GJS callback conventions made the prefs process core-dump on a real Shell 51 ("schema default value ... rejected by the binding mapping function", Extension Manager showed "GNOME Shell Unavailable"). Rows are set from `settings.get_string` when built, written back in `notify::selected`, and follow `changed::<key>` with an echo guard; `window._settings` keeps the settings alive. The preflight skips the connect/disconnect pairing rule for prefs.js (own process, ends with the window). `tests/test-settings.sh` fails if prefs.js uses a binding mapping or a Shell-only import.
- `actions.js` is the single source of truth (no imports, so node can run it in tests): schema id, `BUTTONS`, `CONTEXTS`, `ACTIONS` (id + label), `settingsKey(context, button)` = `<context>-<button>`, `pickAction(read, onDesktop, button)`. Both extension.js and prefs.js import it; the pre-flight WARNs about the extra JS module (fine, it is imported).
- Schema `org.gnome.shell.extensions.desktop-mouse-nav` (`metadata.json` `settings-schema`), string keys with `<choices>` = action ids: `desktop-back` (default `prev-workspace`), `desktop-forward` (`next-workspace`), `anywhere-back` and `anywhere-forward` (`none`). The zip ships the XML only, never `gschemas.compiled` (`just pack` passes `--schema=schemas/...xml` and `--extra-source=actions.js`; verified that the zip then holds no compiled schema).
- Two boolean keys, both default `false`: `work-in-overview` (actions also run while the overview is open) and `work-in-app-grid` (same while the app grid is showing). `overviewAllowed(state, flags)` in `actions.js` decides (grid showing -> only with the grid flag; else overview visible -> only with the overview flag; else always); the handler propagates the press when it says no. `Main.overview.toggle` while the overview is open closes it; the app grid action while the grid is showing is handled in `_toggleAppGrid`.
- Actions, Shell API only (no key synthesis, no processes): `prev-workspace`, `next-workspace` (`workspace.activate`), `toggle-overview` (`Main.overview.toggle()`), `toggle-app-grid` (`Main.overview.showApps()`, hide when the app grid is already showing), `move-window-prev-workspace`/`-next-workspace` (focused NORMAL window not on all workspaces: `window.change_workspace`, then `workspace.activate_with_focus`), `none`. Workspace moves stop at the ends (no wrap, `WRAP` constant).
- Precedence: on the empty desktop the desktop action wins unless it is `none`, then the anywhere action applies; elsewhere only the anywhere action. Unknown ids count as `none`.
- `enable()` gets the settings, caches all four actions (reloaded on the settings `changed` signal) and connects `global.stage` `captured-event`; `disable()` disconnects both and drops the references. No timers.
- Press handler cost: map button 8/9 to back/forward (anything else propagates at once), read the cached actions, propagate when both contexts are `none` (before any actor lookup), propagate when locked or a modal other than the overview is open, only then (desktop action set) run `get_actor_at_pos(REACTIVE)`; the background check is a `Meta.BackgroundActor` or inside `Main.layoutManager._backgroundGroup`, never while the overview is visible. The press is consumed (`EVENT_STOP`) only when an action ran, and the matching release is swallowed; everything else returns `EVENT_PROPAGATE`.
- Logging: none (no `console.log`, nothing in the event handler).

## Versioning (Kevin, 2026-11-09)
Semantic versioning in `version-name`, 0.x until the extension is actually published on extensions.gnome.org. Never propose 1.0.0 before publishing. After publishing, a major bump happens whenever the extension is updated to cover a new GNOME Shell version. A new feature is a minor bump (the settings feature is 0.2.0), a fix a patch bump. `promote` releases only a `version-name` whose tag does not exist yet.

## Testing
```
just lint        # JSON + JS syntax (extension.js is checked as a temp .mjs copy)
just pack        # dist/*.zip (dist/ is gitignored)
just install     # pack, then unzip into ~/.local/share/gnome-shell/extensions/<uuid> (replaces that uuid only)
just enable      # gnome-extensions enable; fails until the Shell knows the extension (log out and in first)
just uninstall   # disable if known, remove the directory
just status      # gnome-extensions info + whether the directory exists
just test        # lint + temp-dir install/uninstall (GNOME_EXTENSIONS_DIR) + tests/test-*.sh; home untouched
just install-release [version] [--dry-run]   # install a released zip, checksum verified
```
`just test` checks packaging, install mechanics and the pipeline scripts, never the extension's runtime behavior (that needs a live Shell). The justfile `uuid` must match `metadata.json` (`install` refuses otherwise).

Manual run: `just install`, log out and in (Wayland), `just enable`, watch logs with `journalctl -f -o cat /usr/bin/gnome-shell` (debug lines need debug logging enabled, e.g. `G_MESSAGES_DEBUG=all`). Test: click Back/Forward on empty desktop, on a window, in the overview.

## CI and release pipeline (build once, promote)
Design (written 2026-11-09, NONE of it has run on GitHub yet when this was written):
- `.github/workflows/ci.yml`, push to `testing` only (no `pull_request` trigger: one run per push; required checks are matched by name). Jobs `test` (Fedora 45 container: `just test` = lint + temp-dir install + `tests/test-*.sh`, schema compile only if `schemas/*.gschema.xml` exists, `just pack`, `scripts/make-manifest.sh`, upload artifact) and `secrets` (gitleaks 8.30.1 over the full history, pinned download with sha256 and `curl --retry`). **Required check names on `main`: `test` and `secrets`; keep them stable.** Artifact name `extension-<tree sha>`, files: `<uuid>.shell-extension.zip` and `manifest.json` (uuid, version-name, commit, tree, zip, zip_sha256, shell-version), kept 90 days. Concurrency cancels an older run of `testing`.
- `.github/workflows/promote.yml`, push to `main`. `scripts/promote.sh` finds the artifact `extension-<tree of the new main commit>` from a run on `testing` with conclusion success (tree equality works for merge, squash and rebase merges; no second-parent logic), downloads it with `gh run download`, checks the zip sha256 against the manifest, manifest tree and uuid, and that `metadata.json` inside the zip has the same uuid and version-name as the tree. Then attest (`actions/attest-build-provenance`) and `gh release create v<version-name>` with the zip and a `.sha256`. Never rebuilds. No matching tested build: the job FAILS and publishes nothing. Only this job has `contents`, `id-token`, `attestations` write (and `actions: read`).
- Versioning: `version-name` in `metadata.json` is bumped BY HAND (EGO: 1-16 characters of letters, numbers, spaces, periods; no hyphens; the promote job also refuses spaces because of the tag). The tag is `v<version-name>`. If the tag exists, promote does not release and ends GREEN with a notice "bump version-name to release" (so merging without a bump releases nothing). No `version` field (EGO assigns it). Testing builds are artifacts only, no pre-release. Merging the first PR with `0.1.0` releases `v0.1.0`. v0.1.0 is released; the next bump (0.1.1) carries the review-guideline fixes.
- `.github/workflows/prepare-ego.yml`, `workflow_dispatch` only (input `ref`, default `main`): builds the zip, runs `scripts/ego-preflight.sh` (FAIL = hard rule, WARN = heuristic), uploads `ego-<version-name>.zip` + `.sha256` + report (zip only when the pre-flight passes) and writes the report plus `scripts/ego-manual-steps.md` into the job summary. It uploads nothing to EGO and stores no credentials (no documented upload API). The pre-flight rules are OUR reading of https://gjs.guide/extensions/review-guidelines/review-guidelines.html (research by the hub, 2026-11-09; the agent has no web access): heuristics, a pass is no guarantee. Severities: FAIL = hard rule (`version` field, empty `donations`, shell-version not majors, more than ONE `.alpha`/`.beta` development entry or a stable major above it, media/script/binary/.po files, minified lines, missed disconnects, ...); WARN = redundant or unverified: `session-modes: ["user"]` (redundant, not banned), `schemas/gschemas.compiled` and a missing LICENSE in the zip ("not stated in the guidelines (unverified)"). `just pack` puts LICENSE into the zip root via `gnome-extensions pack --extra-source=<abs path>/LICENSE` (checked locally: lands at the root; also with a relative path from inside the source dir); `tests/test-pack.sh` lists the zip. The manifest and promote checks only look at the zip sha256, uuid and version-name, so they are unaffected. The guidelines also say AI use is allowed but the developer must be able to justify and explain the code (quoted in `scripts/ego-manual-steps.md`).
- Shexli (optional step in `prepare-ego.yml`, report only): EGO review team's static analyzer, PyPI `shexli==0.2.1`, installed with a uv 0.13.7 musl release download (sha256 checked, `curl --retry`) into a `uv venv --python 3.12`, run on the staged `ego-<version-name>.zip` with `python -m shexli --format text|json PATH` (verified locally; the exit code is 0 even with findings). Output goes to the job summary and the `shexli-report` artifact; the step has `continue-on-error` and ends `exit 0`, never fails the job, and is not authoritative. Local run on the packed zip reported EGO-M-004 for `shell-version: ["51"]` (it considers 51 an implausible future release or invalid, probably an outdated built-in release table; UNVERIFIED reason, a reviewer-facing question for Kevin). Never run on GitHub yet.
- `.github/workflows/gnome-version-watch.yml`, weekly (Wed 06:23 UTC) and manual, in a `fedora:latest` container (the one deliberately unpinned image: it must track the current release): `scripts/gnome-version-watch.sh` runs `dnf repoquery gnome-shell` (queryformat `name|epoch|version|release|arch|repoid`) over channels in order `branched rawhide released` (override with `CHANNELS`), FIRST that answers wins and is logged. `branched` = releasever released+1 with `fedora,updates,updates-testing`; when it does not resolve (no beta yet) it is skipped with a log line. `rawhide` = `--releasever=rawhide` with the repo id READ from `/usr/share/dnf5/repos.d/fedora-rawhide.repo` (package `fedora-repos-rawhide`, installed by the workflow; the stock fedora-repos-45 has no rawhide repo id); without that file the channel is skipped. The major (leading digits, `52.alpha`/`52~beta`/`52~alpha.1` -> 52) is compared numerically with the max of `shell-version`; if larger, one issue `Support GNOME Shell <N>` with label `gnome-version` (created when missing) and a checklist; deduped on any open `gnome-version` issue or same title. Only this workflow has `issues: write`. The version string is only regex-matched, never evaluated. Verified by the hub in a fedora-toolbox:45 container: `--repo`, `--latest-limit`, `--queryformat` work, `--releasever=46 --repo=fedora` returned 51.1. UNVERIFIED: the repo id inside `fedora-rawhide.repo`, the branched channel before a beta exists, and that the workflow has ever run on GitHub.
- Install from a release: `just install-release [version] [--dry-run]` (`scripts/install-release.sh`, uses `gh release download`, checks the `.sha256`, unpacks with the same helper as `just install`, `scripts/install-zip.sh`, which unpacks next to the target and swaps). Idempotent: same version-name installed prints "already installed".
- Settings required in the GitHub repository (Kevin): branch protection on `main` requiring `test` and `secrets`; Actions allowed to create releases and issues (workflow permissions).

## Tests
`just test` runs `tests/test-*.sh` after the temp-dir install: `test-promote` (git temp repo + stub `gh`: tree match, squash-style same tree, checksum mismatch, tag exists, no build, version rules), `test-preflight` (fixtures built from the real extension: version field, extra files, minified line, missed disconnect, deprecated module, constructor/module-load work, metadata rules), `test-pack` (`just pack` zip holds exactly LICENSE, actions.js, extension.js, metadata.json, prefs.js and the schema XML), `test-settings` (schema compiles strict, defaults, keys and choices equal actions.js, button x context -> action via node, extension.js handles every id, prefs.js duplicates none), `test-version-watch` (stub `dnf` and `gh`: 51.1 listed, 52.alpha, 52~beta, 52~alpha.1, rawhide repo id from a .repo file, branched beats rawhide, no beta yet, nothing found, hostile version string, dedupe), `test-install-zip` (temp dir: schema compiled on unpack, zip without schema installs, PATH without glib-compile-schemas fails and keeps the old copy), `test-install-release` (stub `gh`, temp extensions dir), `test-workflows` (YAML parse, SHA pins with version comments, pinned runners, triggers, least-privilege permissions, the Shexli step is optional/pinned/report-only). Stubs live in `tests/stubs/`. Needs `zip`, `jq`, `unzip`; PyYAML for the workflow test (it skips without it).

## UUID
`desktop-mouse-nav@redcodeworks.github.io` stays. Renaming the repo does not change it; changing the UUID would make a different extension for the Shell and for EGO (settings, enabled state). The settings feature landed in 0.2.0 without a UUID change.

## Why install unpacks the zip
The unpack route (`scripts/install-zip.sh`) compiles the schema (`glib-compile-schemas --strict` in the staging directory; fails and keeps the old copy when the tool is missing, Fedora package glib2-devel), because only EGO and `gnome-extensions install` compile it automatically. Found on a real Shell (0.2.0 failed with `GLib.FileError ... schemas/gschemas.compiled: No such file`); CI cannot load the extension in a Shell, so this class of bug is only caught by a real session. A hand-unpacked release zip needs `glib-compile-schemas schemas/` run inside the extension directory.

`gnome-extensions install --force <zip>` failed for Kevin with "Can't recursively copy directory". Probable cause (UNVERIFIED guess): a cross-filesystem move from the temp dir into `~/.local/share/gnome-shell/extensions`. Unpacking the zip directly into the extensions directory avoids it. `SKIP_GNOME_EXTENSIONS=1` makes `uninstall` skip gnome-extensions calls (used by `just test` so a real install of the same uuid is never disabled).
