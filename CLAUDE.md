# CLAUDE.md

GNOME Shell extension `desktop-mouse-nav@redcodeworks.github.io` (GPL-2.0-or-later, public repo `redcodeworks/gnome-shell-extension-desktop-nav`; the local directory keeps the old name `desktop-mouse-nav`). Target: GNOME Shell 51 (Fedora 45, Wayland). Mouse button RULES run an action (mouse buttons only, no keyboard keys): a rule is (button number, modifiers, action id), kept in one list per context: `desktop` (pointer on the empty desktop; default Back/8 = previous workspace, Forward/9 = next, plus since 0.6.0 the Alt wheel defaults below), `shell` (other Shell surfaces such as the top bar), `overview` and `app-grid` (while open; a context with no rules does nothing); edited in the preferences window (0.3.0). Mouse wheel rules (0.4.0, horizontal since 0.5.0) are the same rules with the X11 scroll numbers as the button: 4 = wheel up, 5 = wheel down, 6 = wheel left, 7 = wheel right (see Mouse wheel below). There is NO context for application windows: mutter filters button events before Clutter, so presses on client windows never reach the Shell and a stage `captured-event` handler only sees presses over Shell UI actors (GNOME Shell maintainer on Discourse, 2020, plausibly still valid for 51; not re-verified, hub research). The UI says so; do not reintroduce an "anywhere" context.

## Layout
Subdirectory layout: the extension lives in `desktop-mouse-nav@redcodeworks.github.io/` (`extension.js`, `prefs.js`, `actions.js`, `metadata.json`, `schemas/*.gschema.xml`) so the repo root can hold LICENSE, README, justfile, CI. `gnome-extensions pack <dir>` accepts a source directory, so no flat layout is needed.

## Design
- ESM; `extension.js` default-exports a class extending `Extension`; `prefs.js` a class extending `ExtensionPreferences` (libadwaita: one `Adw.PreferencesPage`; one `Adw.PreferencesGroup` per context in the order desktop, shell, overview, app grid; then groups "Workspaces" (`wrap-workspaces`), "Mouse wheel" (two `Adw.SpinRow`s bound to the wheel keys) and "Advanced" (`debug-log`), switches bound by plain `settings.bind`). Each rule is an `Adw.ActionRow` (0.6.1 layout, left to right: modifier `Gtk.DropDown` as PREFIX, title = button name, action `Gtk.DropDown` and flat `user-trash-symbolic` delete button as suffixes; both dropdowns have a fixed `width_request`, `MODIFIER_DROP_WIDTH` 190 and `ACTION_DROP_WIDTH` 240, guessed from the longest labels and UNVERIFIED in a live session; the add-rule dialog keeps its vertical layout, Kevin 2026-11-10); an `Adw.ButtonRow` ("Add rule", `list-add-symbolic`) closes each list; an empty list shows a dimmed "No rules yet" row. Rows are rebuilt from the setting on `changed::<key>` and after add/delete; in-place edits write back with `settings.set_value(key, new GLib.Variant('a(uss)', ...))` under an echo guard (reading: `get_value(key).recursiveUnpack()`); an edit that would duplicate a rule or make an unbindable one is reverted with a toast. NEVER use `bind_with_mapping` in prefs.js: its GJS callback conventions made the prefs process core-dump on a real Shell 51 ("schema default value ... rejected by the binding mapping function", Extension Manager showed "GNOME Shell Unavailable"). `window._settings` keeps the settings alive. The preflight skips the connect/disconnect pairing rule for prefs.js (own process, ends with the window). `tests/test-settings.sh` fails if prefs.js uses a binding mapping or imports anything but Adw/Gio/Gtk/GLib/GObject.
- Add-rule dialog (`showRuleDialog` in prefs.js): `Adw.Dialog` ("Press a mouse button", libadwaita 1.5) presented with `dialog.present(window)`; on an exception a modal `Adw.Window` with `transient_for` is the fallback. A `Gtk.GestureClick` (`button = 0`, CAPTURE phase) reads `get_current_button()` and `get_current_event_state() & Gtk.accelerator_get_default_mod_mask()` in `pressed`; modifier bits via `modifiersFromState(state, GTK_MASKS, false)` (GDK 4 values hard-coded in actions.js because Gdk is not imported). Buttons 1 and 3 show a message and detection continues (the gesture does not claim the sequence, so Cancel still works). After detection the button, a modifier `Adw.ComboRow` (16 combinations, "None" first) and an action `Adw.ComboRow` appear with Add (disabled while the combination is unbindable or already bound) and Cancel.
- `actions.js` is the single source of truth (no imports, so node can run it in tests): schema id, `CONTEXTS` (desktop, shell, overview, app-grid), `rulesKey(context)` = `rules-<context>`, `ACTIONS` (id + label), the rule model (`makeRule`, `parseRules`, `serializeRules`, `normalizeModifiers`, `MODIFIER_COMBOS`, `modifierLabel`, `buttonName`, `unbindableReason`, `findDuplicate`, `matchRule`, `anyRuleUsesButton`, `contextOrder`, `findRule`, `modifiersFromState`, `GTK_MASKS`) and the rest of the pure logic tests cover without a Shell: `pointerContext`, `resolveAction` (app grid: the page actions -> page step), `pageTarget(current, nPages, step)` (no wrap, null at the ends, one page, zero pages), `workspaceTarget(active, count, step, wrap)`, `hexState`, `debugLine(enabled, button, state, mods, context, found, result, reason)` (null when off). Both extension.js and prefs.js import it; the pre-flight WARNs about the extra JS module (fine, it is imported).
- Schema `org.gnome.shell.extensions.desktop-mouse-nav` (`metadata.json` `settings-schema`): four rule keys of type `a(uss)` (button, modifier string, action id): `rules-desktop`, `rules-shell`, `rules-overview`, `rules-app-grid` (defaults since 0.6.0: see the 0.6.0 section; `[]` before). Modifier strings are normalized and sorted alphabetically: parts `alt`, `ctrl`, `shift`, `super` joined by `+` (`ctrl+shift`), `''` for none. `parseRules` drops invalid entries (buttons 1 and 3, a bare middle button, unknown modifiers or action ids). The old keys `desktop-back`, `desktop-forward`, `shell-back`, `shell-forward` are removed in 0.3.0 without migration (0.2.0 had one user). The zip ships the XML only, never `gschemas.compiled` (`just pack` passes `--schema=schemas/...xml` and `--extra-source=actions.js`; verified that the zip then holds no compiled schema). `glib-compile-schemas --strict` accepts the non-empty tuple-array default (checked, and read back with `gsettings --schemadir` in `tests/test-settings.sh`).
- Two boolean keys, both default `false`: `wrap-workspaces` and `debug-log`. The 0.3.0 switches `work-in-overview` and `work-in-app-grid` (and `overviewAllowed`, the cached flags) were removed before 0.3.0 was released: a context with rules is active, a context without rules does nothing. `Main.overview.toggle` while the overview is open closes it; the app grid action while the grid is showing is handled in `_toggleAppGrid`.
- Buttons and modifiers: any button except 1 (primary) and 3 (secondary), which are refused in the editor and never touched by the Shell side; middle (2) only with at least one modifier. Names: 2 Middle, 8 Back, 9 Forward, others "Button N". Two rules in one context with the same (button, modifiers) are refused in the editor ("already bound"); the Shell side takes the first match. Matching is on the EXACT modifier set: `event.get_state()` is reduced by `modifiersFromState(state, MODIFIER_MASKS, true)` to Shift, Control, Mod1 (Alt) and Super, where Super is `SUPER_MASK` (1<<26) OR `MOD4_MASK` (1<<6), either or both (an entry of the masks object may be several OR-ed bits); `LOCK_MASK`, `MOD2_MASK` and the `BUTTONn_MASK` bits are ignored; any other bit (Hyper, Meta, Mod3, Mod5) makes the press match no rule.
- Actions, Shell API only (no key synthesis, no processes): `prev-workspace`, `next-workspace` (`workspace.activate`; in EVERY context, also the app grid), `toggle-overview` and `toggle-app-grid` (`_toggleOverview`, below), `app-grid-prev-page`/`app-grid-next-page` (`appDisplay.goToPage`, app grid context only), `step-out`/`step-in` and `toggle-quick-settings`/`toggle-calendar` (0.5.0, below), `none`. Workspace moves stop at the ends (no wrap, `WRAP` constant). RESERVED ids (0.4.1): `move-window-prev-workspace`/`-next-workspace` stay known ids and are never to be reused, but are not offered in the editor and their dispatch in `_runAction` is commented out ("disabled in 0.4.1, still hidden in 0.5.0, needs a window-selection fix"; `_moveFocusedWindow` is commented out too). A saved rule with one of them is kept by `parseRules`, shows as "Unavailable in this version" (no action dropdown, the modifier can still be changed, delete works), behaves as Do nothing (propagates, never swallowed) and the debug line says `reason=unavailable-in-this-version` (`actionAvailability`). The editor offers per context only what can work (`actionsForContext`/`notInContext`: the page actions only in the app grid, the panel menu actions only in desktop and shell; a hand-edited action in a list that does not offer it shows "Not available in this list", `reason=not-in-this-context`).
- Context resolution (`pointerContext`, `findRule`, `contextOrder`): with the overview open the context is `app-grid` or `overview` and only that context's rules are tried; otherwise `desktop` (pointer on the empty desktop) tries the desktop rules first and then the shell rules, and `shell` (another Shell surface) tries only the shell rules. First matching rule wins. These replace the 0.2.0 behavior where the overview and app grid used the desktop action.
- App grid paging (0.4.1 changed this): ONLY the `app-grid-prev-page`/`app-grid-next-page` actions page the grid, via `resolveAction`/`pageTarget`, `appDisplay.goToPage(_grid.currentPage -/+ 1)` (clamps, no wrap; at the first/last page or with the grid unavailable the press propagates; `IconGrid.goToPage` throws, so only `AppDisplay.goToPage` is called). In 0.4.0 and earlier `prev-workspace`/`next-workspace` paged the grid in the app grid context; 0.4.1 restored them to switching workspaces, with no settings migration: existing app grid rules with those ids now switch workspaces, and users who want paging pick the new page actions (new ids, so nothing to migrate). Grid access: `Main.overview.controls` or `Main.overview._overview.controls`, then `.appDisplay`; app grid detection `controls._stateAdjustment.value >= ControlsState.APP_GRID (2) - 0.001` (namespace import of `overviewControls.js`, fallback 2), else the dash `showAppsButton.checked`. Everything is wrapped so a missing API propagates the press and never throws.
- Overview/app grid toggles (0.4.1, `overviewTransition(action, state)` pure, state hidden/window-picker/app-grid): `toggle-overview`: hidden -> `Main.overview.show()`, window picker -> `hide()`, app grid -> back to the window picker; `toggle-app-grid`: hidden -> `showApps()`, window picker -> app grid, app grid -> window picker. Switching an open overview uses the Shell's own Super+A route (hub research: gnome-shell main/51.1 `_toggleAppsPage`): `Main.overview.dash.showAppsButton.checked = true/false`; `Overview.show()` returns early when already shown, so it cannot switch. If the dash button is missing it falls back to `showApps()`/`hide()` and the debug reason is `no-show-apps-button`; an unknown state gives `unknown-overview-state`. Unverified on a live Shell.
- Wrap: `wrap-workspaces` (cached in `_loadActions`) feeds `workspaceTarget` for workspace switching and window moves (not for app grid pages). One workspace or target equals active: propagate. The trailing dynamic empty workspace counts as the last one. (Actions run as in 0.2.0, including no key synthesis.)
- `enable()` gets the settings, caches the parsed rules of all four contexts (`_loadActions`, reloaded on the settings `changed` signal; a press never reads GSettings) and connects `global.stage` `captured-event`; `disable()` disconnects both and drops the references. No timers.
- Press handler cost: buttons 1 and 3 propagate at once; a release is swallowed only when its press was; a press of a button that no rule in any context uses propagates before anything else (`anyRuleUsesButton`); then locked/modal checks, the exact modifier set, and only when a desktop rule uses the button the `get_actor_at_pos(REACTIVE)` lookup (the background check is a `Meta.BackgroundActor` or inside `Main.layoutManager._backgroundGroup`, never while the overview is visible). The press is consumed (`EVENT_STOP`) only when an action ran, and the matching release is swallowed; everything else returns `EVENT_PROPAGATE`.
- Logging: only with the `debug-log` setting (off by default; zero cost off). One `console.log` line per press of a button other than 1 and 3 (releases are not logged), including presses that were ignored. `console.debug` and `console.info` are dropped by GJS unless `G_MESSAGES_DEBUG` includes `Gjs-Console` (probed by the hub on Shell 51; the 0.3.0 debug line used `console.debug` and was invisible), so the line uses `console.log`. Format (`debugLine`): `desktop-mouse-nav: button=8 state=0x4000000 mods=super context=desktop match=yes rule=desktop[0] action=next-workspace result=ran`, with ` reason=<why>` appended when the press did not run. `state` = raw `event.get_state()` in hex, `mods` = normalized modifiers (`none`, `ctrl+shift`, `other` when unknown bits are held), `match` yes/no, `rule` = `<list>[<index>]` or `none`, `result` = ran/propagated/at-end/ignored. Reasons: `no-rule-uses-button` (ignored, context found only for the log), `locked-or-modal`, `other-modifier-bits`, `no-matching-rule`, `action-threw`. The single `console.log` sits directly under `if (this._debug) {` (via `_pressLine`); `tests/test-settings.sh` checks that and that there is no `console.debug`. Read with `journalctl --user -b -o cat | grep desktop-mouse-nav`. The pre-flight (`scripts/ego-preflight.sh`): exactly one `console.log` directly under `if (this._debug)` is a WARN; any other `console.log` (ungated or repeated) is a FAIL; `console.debug`/`print` stay a WARN.
- Prefs-side Super: the add-rule dialog reads `get_current_event_state() & Gtk.accelerator_get_default_mod_mask()` and compares with `GTK_MASKS.super` = `Gdk.ModifierType.SUPER_MASK` (1<<26, the GDK 4 value). GTK 4's default modifier mask does not include MOD4, so a MOD4-only state could not arrive there; no MOD4 handling was added to `GTK_MASKS` (unverified on a live session; the modifier can be chosen by hand in the dialog anyway).

## Mouse wheel (0.4.0, Kevin's brief 2026-11-09)
- Schema: NO breaking change and no migration. A wheel rule is the existing `(button, modifiers, action)` tuple with button 4 (up) or 5 (down); `makeRule` gives such a rule `input {kind: 'wheel', direction, button}`. Real buttons never use 4 to 7 (mutter numbers extra buttons from 8 via `button - (BTN_LEFT - 1) + 4`, from memory, UNVERIFIED), so 0.3.0 settings read the same and a 0.4.0 wheel rule loaded by 0.3.0 is just a button that never fires. Since 0.5.0 6 and 7 are the horizontal wheel (`WHEEL_LEFT`/`WHEEL_RIGHT`; `wheelButton(direction)` maps a name back to the number), so a 0.4.x rule saved on button 6 or 7 is now a wheel rule (real mice never send 6 or 7; UNVERIFIED, from memory) and, like the others, needs a modifier unless stored bare. Two new keys of type `d`: `wheel-threshold` (default 1.0 notch, range 0.1..20) and `wheel-min-interval` (default 400 ms, range 50..3000); type `d` for both on purpose (plain `settings.bind` to `Adw.SpinRow` `value`, no uint-to-double doubt). Defaults and limits live in `WHEEL_DEFAULTS`/`WHEEL_SETTINGS`; the test compares them with the schema.
- Modifier required by default: `unbindableReason(button, mods, allowBareWheel = false)` refuses a wheel rule without modifier. The editor's dialog has an `Adw.SwitchRow` "Require a modifier" (on; the modifier starts on Ctrl when none is held; off forces no modifier). A stored wheel rule with mods `''` is the explicit per-rule opt-out: `parseRules` keeps it and the rule row shows "No modifier: plain scrolling triggers this rule". Default modifier Ctrl is a guess, see the questions in the PR.
- Detection dialog: besides the click gesture a `Gtk.EventControllerScroll` (BOTH_AXES, CAPTURE) reports Wheel up/down/left/right: the axis with the larger absolute delta wins, vertical on a tie; `dy < 0` = up, `dx < 0` = left (GTK convention, UNVERIFIED). A real click GTK reports as button 4 to 7 is refused ("Not a usable mouse button."). Both see directions AFTER libinput's natural-scroll inversion, like the Shell, so a rule follows the user's current setting; the dialog says so. There is no invert option.
- Extension: `_onCapturedEvent` sends `Clutter.EventType.SCROLL` to `_onScroll`: `get_scroll_direction()` mapped by name (`SCROLL_NAMES`) and, for SMOOTH, `get_scroll_delta()` (`[dx, dy]`) into the pure `scrollInput` (UP/DOWN/LEFT/RIGHT = one discrete notch; SMOOTH = the delta of the dominant axis, vertical on a tie, `dx < 0` = left, signs UNVERIFIED; a zero delta = null = propagate). The button is `wheelButton(input.dir)`. `get_scroll_finish_flags() !== 0` (end of a touchpad/kinetic gesture; guarded with typeof) calls `wheelReset`. Then the same `_handlePress(event, 4|5, input)` as a button (context, exact modifiers, `findRule` with the desktop-to-shell fallback, app grid paging), and only on a match `wheelStep`. A matching wheel event is ALWAYS swallowed (`held` while accumulating or rate limited), so the top bar's own workspace scrolling does not also act; non-matching events propagate. No wheel rule for a direction: `NOT_USED`, propagate at once.
- Emulated events (hub research 2026-11-09, read in mutter/gnome-shell `main`, NOT the 48-51 branches, summary not byte-checked): mutter's native backend emits for a wheel notch a SMOOTH event flagged `CLUTTER_EVENT_FLAG_POINTER_EMULATED` and then a DISCRETE event without the flag; hi-res wheels give several smooth events and a discrete one per crossing of 60 (v120); touchpad/continuous sources are the reverse (real SMOOTH, synthesized DISCRETE flagged emulated, one per 10.0 of delta). Smooth delta is 1.0 per notch (fixed, `DISCRETE_SCROLL_STEP 10.0`). So `_onScroll` skips events with `event.get_flags() & Clutter.EventFlags.POINTER_EMULATED` (`isEmulatedScroll`; `EMULATED_FLAG` undefined when the binding lacks it, then no filtering) and propagates them: one real event per source remains (discrete for a wheel, smooth for a touchpad). The same-time duplicate check in `wheelStep` stays as the fallback. gnome-shell's own `handleWorkspaceScroll` also uses only discrete directions.
- Debug lines for scroll events add `dir=<direction> source=<Clutter.ScrollSource number> flags=0x..` (`scrollMeta`; `?` when the binding gave nothing) to every line, including `reason=emulated` lines for skipped events (these show `button=0`), so the real hardware can be calibrated.
- `wheelStep(state, {dir, amount, kind, time}, {threshold, minInterval})` (pure): (1) a discrete and a smooth event with the same direction and `event.get_time()` are one notch seen twice (UNVERIFIED whether mutter delivers both for a wheel): the second is `duplicate`; (2) within `minInterval` ms after an action everything is dropped and the sum cleared (`rate-limited`), so a burst or a free-spin wheel gives one action per interval; (3) else amounts of one direction add up (a direction change or a pause over `WHEEL_IDLE_MS` = 600 starts again) and reaching the threshold fires and clears the sum. Unit of the amount: 1 per discrete notch; a smooth delta is taken as is, and that one smooth unit equals one notch is UNVERIFIED (the debug line shows `amount` and `acc` so the threshold can be calibrated). Only matched events advance the state. Settings reload resets the partial sum. Horizontal wheel (0.5.0, Kevin: yes): ONE state and the same two settings for all four directions (a notch is a notch on either axis; the direction check already restarts the sum on a change of direction or axis, and one shared rate limit means a diagonal or tilt burst runs one action per interval); no per-axis settings, no invert option (rules follow the system's natural-scrolling setting).
- Debug line for wheel events: `button=wheel-up` (`inputLabel`), result `held` for a swallowed event without action, reason `accumulating`/`rate-limited`/`duplicate`, and ` scroll=smooth amount=0.50 acc=0.50` (`wheelNote`). With debug on every vertical scroll event that reaches the stage is logged (touchpads: many lines). Only one `console.log` exists (`_logPress`, behind `if (this._debug) {`), because the pre-flight FAILs on a repeated one.
- Where wheel events are seen (reasoned from the button case, UNVERIFIED): the same limit applies, mutter's Wayland pointer handling should take scroll events over client windows before the stage `captured-event`, so wheel rules work on the empty desktop, over Shell surfaces and in the overview/app grid, never over application windows. Natural scrolling: libinput inverts before Clutter. Shift+wheel: GTK apps turn it into horizontal themselves, the compositor should not, so a Shift rule should work (if GNOME delivered it as LEFT/RIGHT the debug log would show nothing for it). Clutter facts (`ScrollDirection` UP/DOWN/LEFT/RIGHT/SMOOTH, `get_scroll_delta`, `get_scroll_finish_flags`, typelib symbols the api-probe does not cover) are from memory, not checked against 51.

### Wheel: to verify on a real session (sources: hub research on mutter/gnome-shell `main`, not the 51 branch, not byte-checked)

## Overview and app grid buttons: finding for 0.4.1 (no live Shell, by reading the code)
Kevin reported that normal mouse buttons do not work in the overview and the app grid either. What the code does: with the overview open `pointerContext` returns `app-grid` or `overview` and ONLY that list is tried; the desktop rules are not used there, and `rules-overview`/`rules-app-grid` default to `[]` (only `rules-desktop` ships Back/Forward), so a user who set Back/Forward only on the empty desktop gets nothing in the overview BY DESIGN since 0.3.0 (a context with no rules does nothing). That is the most likely cause and needs no code change. What could not be settled without a live Shell: whether a press over overview actors reaches the stage `captured-event` at all (the overview takes a modal grab; presses over the window picker, workspace thumbnails or app grid icons may be consumed by those actors or truncated by the grab before the stage handler). No fix was built and nothing was hidden: if a rule exists in the Overview/App grid list and still nothing fires, turn on "Log button presses" and look for the `button=8 ... context=overview|app-grid` line: no line = the press never arrives (a limit like windows, then an overview context needs another route), a line with `match=no` = no rule, a line with `result=propagated reason=...` = see the reason. To be checked by Kevin on a real session; if no line appears the Overview and App grid lists should be documented as unreachable for buttons.

## 0.6.0 default rules (Kevin's request 2026-11-10)
- Schema defaults (GSettings default values, written in the exact tuple text the editor saves, `(uint button, 'alt', 'action')`; the XML `<default>` is the one place): Alt + wheel up (4) = `step-in`, Alt + wheel down (5) = `step-out`, Alt + wheel left (6) = `prev-workspace`, Alt + wheel right (7) = `next-workspace`. `rules-desktop` = `[(8, '', 'prev-workspace'), (9, '', 'next-workspace'), (4, 'alt', 'step-in'), (5, 'alt', 'step-out'), (6, 'alt', 'prev-workspace'), (7, 'alt', 'next-workspace')]`; `rules-shell` and `rules-overview` = the four wheel tuples; `rules-app-grid` = the same four with 6 = `app-grid-prev-page` and 7 = `app-grid-next-page`. Every context got all four rules; nothing was left out or hidden (every action is offered in its list; page actions only in the app grid).
- Top bar: the extension handles scroll in the stage `captured-event` handler, which runs before the Activities button, and a matching wheel event is swallowed, so by the code the shell list honors the rules even though the Activities button scrolls workspaces itself. UNVERIFIED on a live Shell; if Alt+wheel over the top bar still does the Activities scroll, drop the four tuples from `rules-shell` (and mention it here).
- Upgrades: GSettings returns the schema default for every user who never wrote the key, so an upgrading user with an untouched list gets the new rules too; a user who edited a list (even to empty) keeps it. No migration. ## Branching (GitLab Flow, production-branch variant; Kevin, 2026-11-09)
Same model as octarine-os (its PR #23). GitHub rulesets enforce it (applied by Kevin and the hub, 2026-11-09); the `pull_request` path of `ci.yml` and `require-testing-branch` are new and were first exercised by the mapping editor PR (#6).
- Environments: dev = the validation run on a PR (`test` and `secrets`, nothing published), UAT = the rolling `testing` prerelease (`just install --testing`), prod = the release (`just install`). `testing` is the integration branch (GitLab's "main"), `main` the production branch. Changes move one way, downstream: `feat/<topic>` or `fix/<topic>` -> PR into `testing` -> PR from `testing` into `main` (the promotion). Fixes go upstream first.
- Merge methods (enforced by rulesets, no bypass): a feature PR into `testing` is squashed, one commit per feature (the squash commit uses the PR title and body); `testing` into `main` is a merge commit. `testing` ruleset: PR required (0 approvals), squash only, required checks `test` and `secrets`, no deletion, no force-push. `main` ruleset: PR required (0 approvals), merge commit only, required checks `test`, `secrets` and `require-testing-branch`, no deletion, no force-push. Repo settings: rebase disabled, merged branches auto-deleted. Direct pushes to `testing` and `main` are blocked.
- Why a merge commit into `main`: promotion must keep `testing`'s commits as ancestors of `main`; a rebase or squash of `testing` into `main` would rewrite them and the next promotion would replay commits already applied. So no back-merge of `main` into `testing` is needed (`main` only ever has merge commits that `testing` lacks, which is harmless). The tree-based promote lookup copes with any merge style anyway.
- Who merges: the project agent may merge its own feature PR into `testing` once the required checks are green (Kevin, 2026-11-09; GitHub does not let an author approve their own PR, so this means merging); when the brief says Kevin merges, it waits. Merging into `main` is Kevin's only.
- Hotfix: fix on a `fix/<topic>` (or `hotfix/<topic>`) branch into `testing`, then promote. There is no shortcut into `main`: the ruleset has no bypass and `require-testing-branch` is required, so even an emergency goes through `testing`; skipping that would need Kevin to change the ruleset himself.
- PR runs are validation only: the zip is built once per change by the push to `testing` (the PR merge into `testing`), and that build is what `promote` releases by tree. So a PR run must never upload an `extension-<tree>` artifact (promote would then see a build that no `testing` run produced) and never run `publish-testing`.
- `require-testing-branch.yml`: job `require-testing-branch`, `pull_request` into `main`, `permissions: {}`, no checkout; fails unless the head branch is `testing` of this repo. Never runs for PRs into `testing`. Make it a required check on `main` next to `test` and `secrets`.
- The other project repos (hub-managed) still commit straight on `testing`; only this repo and octarine-os use feature branches.

## CI and release pipeline (build once, promote)

## Release candidates (Kevin, 2026-11-10)
- The checked-in `version-name` on `testing` and `main` is always the clean target version (`0.6.1`); nobody bumps an rc by hand. CI stamps the testing build: `scripts/stamp-rc.sh EXT_DIR ZIP` (a `ci.yml` step after `just pack`, before `make-manifest.sh`, also on PR runs so they exercise it) rewrites only `version-name` in the ZIP's `metadata.json` to `<target>-rc<N>` (hyphen form, `0.6.1-rc3`). Nothing is committed. The integer `version` (not present today; EGO assigns it) is never touched. The manifest records the zip's `version-name` and `target-version-name` (the tree's); the rolling prerelease title is `testing (<target>-rc<N>, <short sha>)`.
- N (`scripts/rc-number.sh [REF]`): first-parent commits of `testing` (squash merges) since the last release, floor 1. The last release is found BY TREE, because a release tag sits on a `main` merge commit that `testing` does not contain (no back-merge): walk the first-parent history newest first, stop at the first commit whose tree equals the tree of any `v[0-9]*` tag (the tag `testing` is ignored); N = commits walked past. Right after a promotion the tip itself matches (0 commits), so the floor gives 1; the next merge gives 1 too. On a PR run HEAD is the merge commit, so the PR run shows the number its squash will get. `ci.yml` checks out with `fetch-depth: 0` for the tags.
- Promotion (`scripts/promote.sh`): finds the tested artifact by tree exactly as before (artifact `extension-<tree>`, run on `testing` with conclusion success, zip sha256 and manifest tree verified). The tested zip's `version-name` must be `<version>` or `<version>-rc<N>`, and its `metadata.json` must equal the tree's one except for `version-name` (`jq -S` compare). Then it REPACKS: copies the tested zip and replaces the single entry `metadata.json` with the tree's own file (`zip -X`, byte-identical, so the release carries the clean version), checks every other entry has the same CRC and the same file list, and releases that zip (new sha256, `.sha256` of the repack, attestation on the repack) as `v<version>`. Tree-hash argument: the artifact name is the tree of the tested commit, which includes `metadata.json`; the tested zip and the release zip differ only in `metadata.json`, whose content in the release is the tree's committed file, and every other entry is the tested one. The sha256 of the release zip differs from the tested zip's, so the release notes name the tested build (`<target>-rc<N>`) and the run. The promote job needs `zip` on the ubuntu runner (not verified there).
- Nothing else parses `version-name`: `ego-preflight.sh` still FAILS a hyphen on purpose (a stamped zip must never go to EGO; `prepare-ego.yml` packs the clean source), `install-zip.sh` and `install-remote.sh` only display and compare it as free text (so `just install --testing` shows `0.6.1-rc3`), `fedora-next-release.sh` reads the Latest non-prerelease (`gh release view` without a tag) and refuses any tag not `v<digits>...`. `tests/test-rc.sh` covers the count (no tag, one and several merges, after a release, second release, rolling tag ignored) and the stamp; `test-promote` the repack; `test-fedora-next` the lookup; `test-workflows` the step order.
- A promotion PR that is open takes new work: amend its title and body, no extra `version-name` bump; only the rc number moves. Plumbing changes (CI, scripts, docs) carry no bump at all. Caveat: a plumbing-only build on top of an already released version is labeled `<released>-rc<N>` (for example `0.6.0-rc1` after v0.6.0), the next feature bump moves the target.
- When it first runs: the stamp runs at the first `ci.yml` run after this change (the PR run, then the push to `testing`; push events use the workflow file of the pushed commit). The repack first runs at the first promotion whose `main` push contains the new `promote.yml`/`promote.sh` AND whose tested artifact was built by the stamping `ci.yml`, with a version-name that is not yet tagged (if the tag exists promote ends at the notice before it reaches the repack). Until then the repack path is covered only by `tests/test-promote.sh` with a stub `gh`.

## Why install unpacks the zip
The unpack route (`scripts/install-zip.sh`) compiles the schema (`glib-compile-schemas --strict` in the staging directory; fails and keeps the old copy when the tool is missing, Fedora package glib2-devel), because only EGO and `gnome-extensions install` compile it automatically. Found on a real Shell (0.2.0 failed with `GLib.FileError ... schemas/gschemas.compiled: No such file`); CI cannot load the extension in a Shell, so this class of bug is only caught by a real session. A hand-unpacked release zip needs `glib-compile-schemas schemas/` run inside the extension directory.

`gnome-extensions install --force <zip>` failed for Kevin with "Can't recursively copy directory". Probable cause (UNVERIFIED guess): a cross-filesystem move from the temp dir into `~/.local/share/gnome-shell/extensions`. Unpacking the zip directly into the extensions directory avoids it. `SKIP_GNOME_EXTENSIONS=1` makes `uninstall` skip gnome-extensions calls (used by `just test` so a real install of the same uuid is never disabled).
